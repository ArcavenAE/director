## Findings

1. **Sender-workspace misdelivery.** `Bus.inboxSubject` builds
   `agent.<b.self.Workspace>.<team>.<id>.inbox` from the sender's
   `DIRECTOR_WORKSPACE`; the address `agent://<team>/<id>` carries no
   workspace, and the roster lists every workspace's keys as if they were
   addressable. One send from this seat (`aae-orc`) to
   `agent://fleet/fleet-builder-g1-0` returned message id
   `01M2GQHNNX44Z076GATYP6927C`, "accepted for delivery", and landed on
   `agent.aae-orc.fleet.fleet-builder-g1-0.inbox` (`nats stream subjects`),
   while the twin consumer filters `agent.ops2.fleet.fleet-builder-g1-0.inbox`
   (pending stayed 0). R-86's two-tier bus is cross-workspace by definition,
   so a sender-derived subject breaks the load-bearing case. Registered as
   R-92; ticket below.
2. **The twin reads the operator's shared checkout on whatever branch it
   sits.** `TWIN_CWD` is the orc root; the director subrepo there was on
   `finding/shim-contract-bus-reliability-harvest`, so the twin envoy
   reported `sim/design/marvel-twin-manifest-and-cutover.md` and
   `sim/design/shim-timer-heartbeat.md` "do not exist on disk" though both
   are on `main`. The finding-165 shape, now seen by a cast session. The
   session working directory design (marvel#255, ticket aae-orc-het5e for the
   twin) should give the twin its own checkout rather than the operator's.
3. **Plan mode prompts on the shim's MCP tools.** `wait_for_message` raised
   the harness permission dialog in the plan-mode twin builder, so a
   plan-mode cast cannot receive without a human at the pane. Whether a
   `readOnlyHint` annotation on `wait_for_message` and `list_roster` would
   pass plan mode is a one-command check not yet run; director#22 (auto)
   sidesteps it.
4. **Durable consumers accumulate.** Each shim instance creates
   `mcp_<id>_<instance>` with no inactive threshold; after one kill the
   builder has two, and the deleted marvel-builder role's consumer from
   14:24 local is still listed. Every restart adds one, each holding a full
   replay (R-50). Ticket below.
5. **Kill-respawn keeps the name.** With replicas 1, `marvel kill` followed
   by the `always` policy respawned `fleet-builder-g1-0` in one second with
   the same name, so at S0 the bus id survived a restart without the declared
   identity block. This is marvel's documented rule (marvel CLAUDE.md:
   the index is max(existing)+1 with no gap filling, so a single-replica
   role gets its key back); a crashed middle replica of a multi-replica role
   returns under a new index, and shift mints one for every role. Neither
   path was exercised here (shift is 3.1, the director's).
6. **`in_reply_to` and `reply_by` were dropped on the send path.** Found by
   marvel-builder while fixing finding 1: on `main`, `toolSend` decoded its
   arguments into untagged struct fields, and Go's case-insensitive match
   does not bridge the underscore in `in_reply_to`, so the value never
   reached `InReplyTo` or `CorrelationID`. Verified by reading
   `tools.go` at `origin/main`. Every reply sent through the shim so far
   carried no correlation, which is the R-08 shape of a field nothing read;
   3.2 check A's evidence (`in_reply_to` on the receipt) would have failed
   for a reason unrelated to delivery. Fixed with json tags and a
   broker-free round-trip test in director#24 (commit 845990b). No register
   change: it is an instance under R-08 and R-13, not a new requirement.
